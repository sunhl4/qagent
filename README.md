# DeepSeekHarness 企业级自主研发与自动科研平台

本工程是根据本次对话中的图片、需求和公开网络/GitHub 调研重新建立的独立研究与实施工程。

本工程**不依赖当前其他工作区的既有资料**。目标是以 DeepSeek Harness（简称 DSH）作为公司统一的 Agent Harness，也就是统一的智能体运行框架，在其上开发公司自己的 Agent、插件、工作流和多租户服务。

## 与另一台电脑上 harness-core 的关系

公司已在另一台电脑上开发 DSH 工程，并已接入云平台、本地 HPC 和本地模型。本工程与之**平行开发，通过契约合并，不重复实现**。

```text
harness-core（对方）
  DSH 运行时、云平台、本地 HPC、本地模型、身份、存储、凭据
        │ 实现端口
        ▼
@company/dsh-contracts（唯一共享契约）
        ▲ 消费端口
        │
research-platform（本工程）
  目标、任务、实验、证据、策略、审批、预算、领域工作流、报告、前端
```

本工程明确不做：

- 不 fork DSH。
- 不写云平台 SDK 封装。
- 不写 Slurm/HPC 客户端。
- 不部署推理引擎。
- 不建第二套用户、租户、密钥、对象存储。

本工程明确要做：

- 目标到任务的拆解与优先级。
- 24/7 持久工作流与状态机。
- 实验规格、决策规则、停止条件。
- 运行清单、证据链、失败库。
- 文献到复现的完整闭环。
- 软件与前端自动化交付。
- 策略、审批、预算、计量、审计。
- 契约包与一致性测试。

详见 `docs/12_双轨开发与合并策略.md` 与 `docs/13_集成边界与不重复清单.md`。

## 目标

平台面向公司内部多个团队和用户，持续支持以下任务：

1. 算法迭代开发：自动修改算法、申请 CPU/GPU/HPC/云资源、执行计算、保存检查点、回收资源、分析结果，并继续下一轮。
2. 文献阅读与算法复现：检索论文、解析全文、抽取方法、定位代码、构建环境、复现基线、比较差异、分析失败原因。
3. 自动研究：从文献缺口和历史实验中生成候选假设，设计消融实验，经过预算与策略审核后进入算法实验循环。
4. 软件和算法架构开发：自动完成需求拆分、编码、测试、前端浏览器验证、安全扫描、代码审查和发布候选构建。
5. 多用户交付：每个用户或团队可以使用相同的平台能力，但具有独立的租户、项目、预算、凭据、数据和运行记录。
6. 模型可替换：既支持 DeepSeek API，也支持公司自部署模型、私有推理服务和采购的第三方模型。

## 重要架构结论

DSH 适合作为：

- Agent 交互入口
- 插件运行时
- 工具和模型适配层
- 会话与执行上下文层
- 公司内部 Agent 的统一扩展底座

DSH 不应独自承担：

- 数天或数月运行的持久化业务工作流
- 跨系统任务的最终一致性和补偿
- HPC、GPU、量子硬件或云资源的权威调度
- 企业级租户、预算和计费事实源
- 生产环境的最终权限边界
- 真实硬件的安全控制闭环

推荐的组合是：

```text
DeepSeek Harness / Cordis
    负责 Agent、插件、工具、模型路由和会话

上游 Super-agent（计划按五模块全部开源接入，本工程不实现）
    负责仓库内编码协作：Router / Worker、工单、多信道、重启后续跑

Temporal 或同类持久工作流引擎
    负责实验、租约、审批和跨天恢复

Slurm / Kubernetes + Kueue / SkyPilot
    负责 HPC、GPU、云和批任务资源

PostgreSQL + 对象存储 + MLflow/DVC
    负责状态、实验、数据、模型、日志和 provenance

策略、审批、短期租约和沙箱
    负责多用户安全与高风险动作控制
```

## 推荐首版技术栈

- DSH：公司统一 Agent Harness
- 上游 Super-agent：编码协作运行时。五模块按开源假设接入；未冻结前阶段 4 降级为单工单 headless
- Cordis 插件：公司能力扩展的主要组织方式
- Temporal：长流程和后台任务总控
- PostgreSQL：任务、租户、预算、审批和状态索引
- S3/MinIO：源码、数据、日志、检查点、结果和报告
- Slurm：自有超算和 CPU/GPU 集群
- Kubernetes + Kueue：容器化批任务和配额
- SkyPilot：跨云 GPU、Kubernetes、Slurm 和自动回收
- MLflow：实验、模型、Agent trace 和评测
- DVC：数据、模型和实验输入版本
- Optuna/Ax：算法搜索和主动实验
- pytest + Hypothesis + Testcontainers：后端测试
- Playwright：前端端到端测试和 Agent 浏览器操作
- CodeQL/Semgrep/Trivy/Syft：安全与供应链
- OpenTelemetry：跨 DSH、工作流、资源和前端的统一观测

## 双工程分工

公司已在另一台电脑开发 `harness-core`，包含 DSH 接入、云平台、本地 HPC、本地模型、身份、存储与凭据。本工程是 `research-layer`，只做研究层，不重复基础设施。

```text
harness-core：能不能跑、在哪里跑、用哪个模型、谁能访问
research-layer：做什么研究、怎么验证、保留还是撤销、下一步做什么
```

两侧只通过 `contracts/` 的 9 个端口集成，契约版本 `0.1.0`。本工程可在只有桩的情况下独立编译、测试和运行；合并时替换端口实现即可，不改业务代码。

详见 `docs/12_双轨开发与合并策略.md`、`docs/13_集成边界与不重复清单.md` 与 `contracts/README.md`。

## 关键原则

- Agent 是建议和执行的参与者，不是企业事实源。
- DSH 插件负责能力接入，持久工作流引擎负责长时间状态。
- 所有高成本或不可逆动作必须经过服务端策略检查。
- 所有外部资源都通过短期租约和幂等请求访问。
- 执行状态未知时先对账，不能盲目重试。
- 代码、数据、环境、模型、实验和结果必须可追溯。
- 失败结果必须保留，不能只保存成功实验。
- 模型可以替换，工作流对象和实验数据不能绑定某一家模型供应商。
- 正式论文、正式软件发布和真实硬件实验不能完全无人审批。

## 当前状态

这是研究和架构设计工程，不代表已经完成 DeepSeek Harness 生产部署。DeepSeek Harness 的公开资料显示其处于 public preview，核心插件和 API 仍可能变化。因此正式开发前必须：

- 固定 DSH 仓库 commit 或发行版本。
- 建立公司内部插件 conformance suite。
- 为每个 DSH API 依赖保留适配层。
- 不把 preview API 直接写进长期数据格式。
- 先在沙箱和模拟资源上完成 24 小时稳定性测试。

当前已具备：

- 15 份架构、实施与协作文档。
- 20 份领域对象 schema。
- 2 份跨工程契约 schema（能力描述、集成清单）。
- 9 个 TypeScript 端口定义。
- 8 个可运行的本地桩，全部声明 degraded。
- 36 条端口一致性用例（35 条 MUST）。
- 157 个测试，覆盖未知执行、预算、审批、缺失产物、失败分类、失败库、有界循环、日报、worktree、租约（单项与循环级）、成本账本、检查点恢复、执行对账、自动回收、泄漏告警、多种子复现、文献去重、方法卡、语料落盘、假设质量门、软件合并门禁与记录 schema。
- 1 个可交互 Canvas。

运行：

```bash
make check
```

当前不具备（需要 harness-core 或公司基础设施提供）：

- 真实 DSH 版本锁定。
- 真实云、HPC、模型适配器。
- 真实身份、存储、凭据服务。
- 生产部署脚本与压测报告。
