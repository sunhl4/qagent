# 四类范式组合决策

## 0. 结论

这些方案不是竞争关系，而是分层：编码协作用上游 Super-agent，实验与治理仍用原来的主实现。

| 层次 | 采用 | 具体落法 |
|---|---|---|
| 方法层 | Superpowers | 把澄清、设计、计划、TDD、审查、收尾做成 Executor 技能，并由服务端门禁强制 |
| 规格入口 | spec-kit | 规格先落盘，再成为工单授权范围 |
| 实验协议层 | autoresearch | 固定预算、固定指标、受限修改面、保留或撤销 |
| 编码协作层 | 上游 Super-agent | Router / Worker、Trigger、Ticket、订阅直通、存算分离、Watchdog。本工程不实现 |
| 实验外循环 | Temporal | 每次实验尝试使用新上下文；吸收 Ralph 的三条语义，不落地它的 shell 循环 |
| 独立评审 | pr-agent 或只读评审工单 | 作者 Agent 不审查自己打开的 PR |
| Harness 层 | DSH（替代 Pi） | 插件化运行时。Pi、OpenHands 与其他编码代理不部署 |

2026-11-01 起，编码协作按「Super-agent 五模块会完成并开源」规划。假设、两套时钟和降级见 `docs/15_Super-agent接入与两套时钟.md`。

## 1. Superpowers

### 1.1 它解决什么

编码 Agent 的通病是“想到哪写到哪”。Superpowers 用强制流程把它变成：

1. 先澄清需求。
2. 再给设计。
3. 再拆计划。
4. 每个任务先写失败测试。
5. 实现后审查。
6. 收尾时验证并决定合并方式。

### 1.2 可直接吸收的部分

| 机制 | 为什么有效 | 在 DSH 中的实现 |
|---|---|---|
| 需求澄清 | 减少错误方向上的浪费 | `goal` 插件的结构化问答 |
| 设计文档 | 让计划可审查 | 产物写入对象存储 |
| 小任务计划 | 每步可在单上下文完成 | 平台任务表拆分为子任务 |
| 严格 TDD | 提供机器可判断的完成信号 | `software` 插件强制先跑失败测试 |
| 分级审查 | 阻断关键问题 | 评审结果进入合并门禁 |
| 分支收尾 | 避免半成品堆积 | 自动生成 PR 或丢弃 |

### 1.3 不可照搬的部分

- 它的插件格式是面向多个 coding agent 的，不是 DSH 原生格式。
- 它依赖模型自觉执行技能，企业环境必须由服务端强制。
- 它的“完成”是语义判断，平台需要可执行的验收测试。
- 它的会话仍在单一上下文里，长任务需要外循环。

### 1.4 公司版流程

```text
需求录入
→ 结构化澄清（目标/非目标/验收/风险）
→ 设计草案（接口/数据/失败模式）
→ 计划拆分（每项 ≤ 30 分钟，含验证命令）
→ 人工或策略批准
→ 隔离 worktree
→ RED：写失败测试并确认失败
→ GREEN：最小实现
→ REFACTOR：清理
→ 单测 + 集成 + E2E
→ 静态安全 + 依赖扫描
→ Agent 评审
→ 人工审批
→ 合并/丢弃
```

## 2. autoresearch

### 2.1 它解决什么

把“研究”变成一个可重复、可比较的工程循环：

```text
改代码
→ 固定预算训练
→ 测固定指标
→ 比基线
→ 保留或撤销
→ 记录
```

### 2.2 四个核心约束

| 约束 | 原文做法 | 公司升级 |
|---|---|---|
| 固定预算 | 每次 5 分钟 | 每类实验声明预算（wall-clock / GPU-hours / 核时） |
| 固定指标 | val_bpb | 主指标 + 护栏指标 + 统计不确定性 |
| 单一修改面 | 只改 train.py | 允许清单 + 禁止清单 + 变更大小上限 |
| 保留或撤销 | 人工看结果 | 预注册决策规则 + 人工复核门 |

### 2.3 必须补的六个缺口

原项目是单 GPU 研究原型，直接搬到企业会有六个缺口：

1. **无资源调度**：不能申请/排队/回收 HPC。
2. **无多租户**：不能隔离用户与预算。
3. **无失败分类**：失败只记录，不归类。
4. **无统计检验**：单次结果可能被噪声误导。
5. **无 provenance**：代码、数据、环境未形成证据链。
6. **无审批**：高成本动作没有门。

### 2.4 公司版实验协议

每个实验必须声明：

```yaml
hypothesis: "明确、可证伪"
baseline:
  source: "已复现的基线"
  metric_value: 0.0
variables:
  changed: ["只列允许修改的面"]
  controlled: ["数据、划分、评测、硬件"]
metrics:
  primary: "主指标"
  guardrails: ["护栏指标"]
  statistic: "均值/中位数/置信区间"
  repeats: 3
resources:
  type: "cpu|gpu|hpc|qpu"
  max_wall_clock: "2h"
  max_cost: "预算上限"
stopping:
  max_attempts: 5
  max_consecutive_failures: 2
  early_stop: "规则"
decision:
  keep_if: "主指标改善 ≥ 阈值且护栏不退化"
  discard_if: "任一护栏退化或成本超限"
artifacts:
  required: ["code_hash", "env_lock", "raw_metrics", "logs", "manifest"]
approval:
  required_for: ["gpu_gt_1", "hpc", "qpu", "cost_gt_threshold"]
```

## 3. Ralph

### 3.1 它解决什么

长任务的主要问题是上下文腐化。Ralph 的做法是：

- 每轮启动全新实例。
- 只靠 Git、任务清单、进度文件传记忆。
- 每轮只做一个最小任务。
- 用可机器判断的完成信号退出。

### 3.2 三个可复用直觉

1. **上下文要短**：长会话的边际收益递减，错误累积。
2. **状态要外置**：模型记忆不可靠，文件与数据库可靠。
3. **完成要可验证**：不能靠模型说“我完成了”。

### 3.3 不可照搬的部分

| 原型做法 | 问题 | 公司替代 |
|---|---|---|
| `while true` shell | 无恢复、无预算、无并发控制 | Temporal 工作流 |
| `prd.json` 本地文件 | 无并发、无审计、无权限 | Postgres 任务表 |
| `progress.txt` | 非结构化、易膨胀 | 结构化记忆 + 失败库 |
| 最大迭代次数 | 单一停止条件 | 预算 + 时间 + 失败率 + 截止期 |
| 无沙箱 | 任意执行 | 分级沙箱 |

### 3.4 公司版外循环

编码与实验使用两套时钟，详见 `docs/15_Super-agent接入与两套时钟.md`。

编码工单走上游 Super-agent：Source 产生 Trigger，Eval 决定是否授权，Executor 在独立目录中执行，后续讨论经订阅回到同一工单。本工程不另写这个循环。

实验尝试仍由 Temporal 驱动，并且每轮使用新上下文：

```text
Temporal 工作流：
  loop:
    1. 取下一个可执行实验尝试（优先级 + 依赖 + 预算）
    2. 检查是否超过停止条件
    3. 创建隔离工作区
    4. 启动一次新的 DSH headless 会话（单次尝试、有限工具、有限时长）
    5. 收集结构化结果与产物
    6. 按预注册规则决策：保留 / 撤销 / 停止
    7. 写入运行清单、记忆与失败库
    8. 释放资源
    9. 决定下一步：继续 / 等待 / 升级人工 / 终止
```

需要改实验代码时，可以把该尝试的代码修改交给一张 Super-agent 工单。工单结束只是平台时钟的一个信号，不代替指标、清单和租约结算。

## 4. Pi 与 DSH 的取舍

### 4.1 Pi 的启示

Pi 的公开定位是“最小、可扩展的 harness”，明确不内置权限系统，需要容器或沙箱提供边界。它的价值是证明：

- Harness 应该小。
- 扩展应该通过包/插件。
- 必须可嵌入（RPC、SDK、JSON 模式）。
- 安全边界在 harness 之外。

### 4.2 为什么选 DSH

| 维度 | Pi | DSH |
|---|---|---|
| 插件模型 | 扩展/技能/包 | Cordis 服务 + 事件 + 可逆副作用 |
| 事件系统 | 有扩展点 | 类型化事件，含 waterfall/bail |
| 运行形态 | CLI/TUI/RPC/SDK | Web/桌面/headless/SDK |
| 沙箱 | 外包 | 提供 `ctx.sandbox` 抽象与 `SandboxProvider` |
| 生态 | 社区 | 官方 + 社区插件 |
| 公司可控性 | 需 fork 或包封装 | 插件层可完全自研 |

选 DSH 的核心理由：**公司要做的是“在上面深度开发自己的 agent”，需要的是稳定的服务/事件/沙箱抽象，而不是再包一层 CLI**。

### 4.3 保留 Pi 作为参考

- 参考它的最小化设计，避免插件层过度耦合。
- 参考它的 RPC/SDK 形态，确保平台可驱动。
- 不把 Pi 的“无权限系统”当作可接受的安全模型。

## 6. 常见误解

| 误解 | 纠正 |
|---|---|
| “有了 autoresearch 就能自动科研” | 它只提供实验循环，不提供文献、复现、资源和治理 |
| “Ralph 能跑 24 小时就是生产可用” | shell 循环没有恢复、预算、并发和审计 |
| “DSH 有定时任务就不需要工作流引擎” | 定时任务不等于持久状态机 |
| “插件可扩展就等于权限隔离” | 权限必须由沙箱和策略层强制 |
| “换更强的模型就能解决可靠性” | 可靠性主要来自状态、验证和边界设计 |
| “Super-agent 开源后可以替换 Temporal、Slurm 和实验协议” | 它承接编码协作。实验、租约、证据和调度仍用原主实现 |
| “原计划的 router 就是 Super-agent Router” | 原 router 是模型路由，引擎用 DeepInfer / vLLM / SGLang / TensorRT-LLM，网关在 harness-core。LangGraph 没有被选成路由器 |
| “Walking Cat 可以替换 Watchdog” | Walking Cat 是囚禁离子 qLDPC 架构。它只给量子轨道做设计参考；Agent 监督仍只报告，不改写策略 |
| “Watchdog 可以自动重试未知执行或修改策略” | Watchdog 只报告进展异常。未知执行、预算和审批仍由平台决定 |
