# 双轨开发与合并策略

## 0. 前提与约束

已知事实：

- 另一台电脑上已有 DeepSeekHarness 的工程。
- 对方已接入云平台、本地 HPC、本地模型。
- 本工程看不到对方代码、接口和数据结构。
- 两边要独立开发，后期合并，且不能重复实现同一能力。

因此本工程采用**契约优先的平行开发**：

```text
对方工程（harness-core）
  负责：DSH 运行时、云平台适配、本地 HPC 适配、本地模型服务、基础身份
        │
        │ 实现端口
        ▼
  契约包 dsh-contracts（唯一共享真相）
        ▲
        │ 消费端口
        │
本工程（research-platform）
  负责：目标/任务/实验/证据/策略/审批/预算/领域工作流/报告/前端
```

关键判断：**合并的对象不是代码，而是契约。** 两边代码可以完全不同，只要都满足 `dsh-contracts` 的版本与语义，就能拼装。

## 1. 为什么不能让两边都写适配器

如果本工程也写一套云、HPC、模型适配器，会产生：

- 两套凭据体系
- 两套重试与幂等语义
- 两套资源状态机
- 两套计费口径
- 两套错误码
- 合并时大面积冲突

结果是“合并”变成“重写”。所以本工程明确不碰这些适配器的内部实现，只定义它们必须满足的端口。

## 3. 唯一共享物：契约包

### 3.1 位置与发布

```text
contracts/                # 本仓库路径；包名仍为 @company/dsh-contracts
  package.json        # @company/dsh-contracts
  src/types.ts        # 通用类型
  src/ports/*.ts      # 端口接口
  schemas/*.json      # 载荷 schema
  conformance/        # 一致性用例
```

合并进入对方 monorepo 后，目录可迁到 `packages/dsh-contracts/`，包名、版本和导出保持不变。

发布方式二选一：

| 方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 私有 npm registry | 版本清晰、依赖简单 | 需运维 registry | 推荐 |
| Git submodule / subtree | 无需 registry | 版本漂移、合并痛 | 备选 |
| 复制文件 | 最简单 | 必然分叉 | 禁止 |

### 3.2 版本规则

- 语义化版本。
- 主版本：破坏性变更（删字段、改语义、改单位）。
- 次版本：新增可选字段或新端口。
- 补丁：文档、注释、测试。
- 双方 `package.json` 必须锁定同一主版本。
- 升级契约必须双方同时评审。

### 3.3 兼容规则

- 消费方必须忽略未知可选字段。
- 不得忽略未知状态值；必须映射到 `unknown` 并告警。
- 不得把供应商状态直接透传为平台状态。
- 新增能力必须通过 `describe()` 声明，不得假设存在。

## 4. 两类接缝

### 4.1 DSH 插件内接缝（Agent 侧）

本工程的 DSH 插件通过 `ctx` 访问对方提供的服务：

```text
ctx.modelGateway   ← 对方实现
ctx.compute        ← 对方实现（云 + HPC）
ctx.artifactStore  ← 对方实现
ctx.identity       ← 对方实现
ctx.secrets        ← 对方实现
ctx.events         ← 对方实现
```

本工程插件只依赖这些键，不 import 对方实现。

### 4.2 平台服务接缝（工作流侧）

Temporal Activity 不直接调用云 SDK，而是调用本工程的 `IntegrationGateway`，由它转发到：

- 对方的 HTTP/gRPC 服务，或
- 对方提供的 DSH 插件服务（通过 SDK 驱动）。

两种都允许，但**同一能力只能选一种主通道**，避免双写。

### 4.3 推荐组合

| 能力 | 主通道 | 原因 |
|---|---|---|
| 模型调用 | DSH 插件内 `ctx.modelGateway` | 与 Agent 会话同进程，延迟低 |
| 云/HPC 作业 | 平台服务 HTTP | 长流程、需独立重试与对账 |
| 对象存储 | 平台服务 | 工作流与插件都要用 |
| 身份校验 | 平台服务 | 统一入口 |
| 短期凭据 | 平台服务 | 不经 Agent 上下文 |
| 领域事件 | 事件总线 | 跨进程 |

## 5. 契约冻结与演进

### 5.1 三阶段

```text
阶段 A：草案（v0.x）
  本工程定义端口与 schema，对方评审，允许调整。

阶段 B：冻结（v1.0）
  字段、语义、错误码固定；只允许向后兼容新增。

阶段 C：扩展（v1.x）
  新端口、新可选字段；不改既有语义。
```

### 5.2 冻结检查

- [ ] 每个端口有 `describe()`
- [ ] 每个方法有错误码表
- [ ] 每个状态有终态定义
- [ ] 幂等键规则明确
- [ ] 超时与重试规则明确
- [ ] 未知状态处理明确
- [ ] 单位与时间格式明确
- [ ] 双方各有一致性测试

## 6. 防重复的工程手段

### 6.1 目录所有权

合并冲突的本质是同一文件被两边改。用 glob 划分所有权：

| 路径 | 所有者 |
|---|---|
| `packages/dsh-contracts/**` | 共同（需双方 review） |
| `harness-core/**`（对方仓库） | 对方 |
| `platform/**`（本工程） | 本工程 |
| `docs/**` | 本工程 |
| `schemas/**`（本工程领域） | 本工程 |
| `deploy/**` | 共同，按环境分文件 |

规则：**不要跨所有权边界修改**。需要变更对方代码时，提 issue 或 PR，不直接改。

### 6.2 禁止清单

- 禁止 fork DSH 后各自修改核心。
- 禁止在本工程实现云/HPC/模型适配器。
- 禁止在对方工程实现实验/证据/审批逻辑。
- 禁止两边各建一套用户与租户表。
- 禁止两边各建一套计费口径。
- 禁止复制粘贴对方的 DTO。
- 禁止在契约外传递隐式约定。

### 6.3 反腐蚀层

即使契约一致，两边内部模型也不同。每边内部都要有映射层：

```text
对方内部模型 → 对方 Adapter → 契约 DTO
契约 DTO → 本工程 Anti-Corruption Layer → 本工程领域对象
```

规则：

- 领域对象不直接使用契约 DTO。
- 映射层集中，不散落在业务代码。
- 映射层有单元测试。
- 契约升级只改映射层。

## 8. 集成环境

```text
本工程开发环境
  └─ 本地桩（stub）实现全部端口
       ├─ 假模型网关（固定响应 + 延迟 + 成本）
       ├─ 假算力（内存队列 + 模拟状态机）
       ├─ 本地文件对象存储
       └─ 内存事件总线

联调环境
  └─ 对方真实实现
       ├─ 云平台
       ├─ 本地 HPC
       └─ 本地模型

生产环境
  └─ 双方合并部署
```

桩实现的价值：**本工程不需要等对方，就能完整开发与测试**。

## 9. 合并步骤

```text
1. 确认契约版本一致
2. 对方跑一致性测试
3. 本工程跑一致性测试
4. 起联调环境
5. 跑端到端冒烟
6. 检查能力声明与降级
7. 检查错误码映射
8. 检查用量与成本口径
9. 检查权限与租户
10. 灰度
11. 回滚演练
12. 合并
```

## 附录 C：五阶段合并路线

| 阶段 | 目标 | 退出条件 |
|---|---|---|
| 0 契约冻结 | 确认 `0.1.0` 端口、错误码、未知执行语义 | 双方签字/tag |
| 1 一致性 | 双方各自跑 `cases.yaml` | MUST 全过，差异入 `knownLimitations` |
| 2 影子联调 | 同一实验同时走桩与真实端口 | 状态、产物哈希、决策一致 |
| 3 适配器替换 | 逐端口替换：ArtifactStore → Identity/Secrets → ModelGateway → Compute | 每次替换后全量测试通过 |
| 4 灰度 | 小预算、单租户、非敏感数据 | 错误率、未知执行、成本、释放达标 |
| 5 代码合并 | 统一包名、构建、CI、版本 | 重复实现删除，发布流程统一 |

阶段 3 的替换顺序建议从“无副作用”到“有副作用”：先存储与身份，再模型，最后算力。

## 附录 D：合并冲突预防

| 冲突点 | 预防 |
|---|---|
| 同名包 | 统一 scope：`@company/dsh-*` 与 `@company/research-layer-*` |
| 重复 DTO | 以 `contracts/src/types.ts` 与 `ports/*` 为准 |
| 重复错误码 | 只用 `PortErrorCode` |
| 重复状态机 | 本工程拥有研究任务状态机；core 拥有资源状态机 |
| 配置格式 | 本工程只读自己的配置；端口连接信息由 core 注入 |
| 时间与 ID | 统一 ISO8601 与 ULID/UUIDv7 |
