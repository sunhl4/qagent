日期：2026-10-21 09:33（UTC+8）需求澄清。  
状态：集成设计；本次不安装组件、不改变生产配置或工具权限。  
沿用：[v0.5 界面基准](workspace-ui-baseline-v0.5.zh-CN.md) 与 [v0.6 通用能力验收](company-agent-general-capabilities-v0.6.zh-CN.md)。本版修正实现方式：优先复用 DSH 和现成扩展，不把每项通用能力都视为待自研子系统。

## 一、准确定位

**公司产品是在 DeepSeek Harness（DSH）上集成公司本地大模型、受管插件、MCP 服务和常用 Skills，形成日常可用的通用 Agent。量子算法只是其中一类服务能力。**

用户平时写文档、处理文件、编程、调研和分析数据，与使用通用 Agent 一样；需要公司知识、云平台、HPC 或量子计算时，在同一对话中使用获准能力。不要求所有任务经过算法目录，也不要求为了写周报先连接量子云。

我们的主要建设内容是：选型与装配、公司接口适配、Skills 整理、本地模型适配、账户与数据权限、插件接口鲁棒性，以及既定三栏工作空间。已有 DSH 会话 / 模型 / 工具生命周期、成熟云平台、HPC、知识正文和推理服务继续复用。

## 二、各部分分别负责什么

- **DSH**：唯一 Agent Runtime，负责模型交互、会话、工具生命周期及其原生 UI / 扩展机制。右栏直接使用原生对话，不另做一套聊天或执行循环。
- **本地模型**：使用公司已部署模型和 DeepSeek，由 DSH 的模型适配接入。验证流式工具参数、上下文、并发、限流与数据策略；不重建推理平台，也不默认回退公网模型。
- **插件**：运行时扩展、工具注册、策略或界面集成机制。优先选用固定版本可复用的实现；本仓 `packages/` 的公司工具插件仍只注册并转调 `company-agent invoke`，不放业务逻辑。
- **MCP**：Model Context Protocol，用于连接工具和资源服务。它是接入协议，不是新的 Agent，也不替代公司权限、审批、结果校验和服务端业务规则。
- **Skill**：复用团队的工作方法、步骤、模板与检查要求，告诉模型如何使用已经获准的工具。Skill 本身不签发权限、不产生工具，也不成为新的后台 Agent 循环。
- **公司服务**：云平台负责自己的任务 / 结果 / 费用，HPC 负责集群作业，知识库负责资料与权限，算法平台负责科学实现与动态能力目录。它们并列接入，不把量子算法作为所有能力的上级入口。

插件与 MCP 可以组合使用：插件负责在 DSH 注册能力，适配器通过 MCP 连接后端；也可以直接接现有 HTTP API。采用其中一种，不要求每个服务同时建设插件、MCP server 和新微服务。

## 三、复用优先，只有缺口才补开发

### 通用能力

文件、编辑、搜索、网页、命令、办公、分析等先检查 DSH 固定版本和成熟插件 / MCP 是否满足需要。可复用就做受管装配、隔离配置和验收；缺少协议或结果映射时写薄适配；仅确实缺失的执行能力才新增实现。

v0.6 的“隔离执行服务”指必须有安全的执行边界，不意味着必须自研一整套远程开发平台。可复用已验证的沙箱、容器或既有开发服务。生产仍只用受管组合，不能为方便打开内置 shell preset 或任意用户 preset。

### 公司服务

- 已有正式 API：保留 API，补必要的授权与合同适配，不为统一品牌全部转成 MCP。
- 已有合格 MCP：固定服务身份、版本、工具映射和授权范围，复用其传输 / 生命周期机制；核对 DSH 当前版本是否支持所需特性。
- 没有可复用接口：对现有业务能力做最薄封装，业务事实源仍在原系统，不复制队列、账本或算法实现。
- 某服务暂不可用：标记该能力不可用并诚实解释；其他无依赖任务仍应可用。涉及授权或完整性不确定的调用失败闭合。

“已安装”“已配置”“已连接”“已获授权”“已通过真实任务验收”分别记录，不混为一个绿色状态。

## 四、公司合同与 MCP 如何共存

MCP 解决“如何连接”，项目合同解决“允许向模型暴露什么、如何校验、由谁执行”。采用 MCP 不取消 `contracts/` 真源。

当前公司工具调用路径继续为：DSH 注册的公司工具 → `company-agent invoke` → Python 合同 / 策略校验与南向适配 → 既有业务服务。若南向使用 MCP，则在受管适配边界完成会话、调用与结果映射；不把 MCP 原始响应直接当成已有 `company-agent-provider/1.0` 信封。

通用上游工具或 MCP 直连若要进入受管组合，先明确工具白名单、合同映射、身份、审批与结果边界，并同步实际会话工具清单门禁。可以复用 DSH 的原生 MCP 客户端，但不能靠动态发现就把任意新工具自动暴露给模型，或绕开现有 Company Agent 校验。选择直连还是适配，由实际兼容性决定，不预先强制再建一套通用网关。

工具名称加受控命名空间并固定映射；同名冲突、声明变更或未知工具拒绝装配或隔离待审。工具名称 / 版本准入与算法动态目录不同：不把具体量子算法固化为每个算法一个工具。

量子能力继续遵守：

- 只从平台 `algorithm.catalog` 发现 `component_id`，执行绑定目录与组件版本；Skills 和知识库不固化可执行算法清单。
- Agent 不直接 import 科学包；完整电路和大结果经授权内容通道展示，模型仅接收允许的短结果。
- 句柄只有 `asset_id`、`circuit_id`、`twin_id`；只有 `quantum_device_run` 且 provider 为 `ionstack-twinrun` 可以返回 `twin_id`。
- 设备在 `lab / sign` 必须 ask，在 `boot / algo` 必须 deny；MCP、算法执行、普通命令或内部用户不能成为旁路。
- 官方 Codex 继续保持宿主 provider、`permissionMode: never`、`inheritsParentContext: false`，不开放模型可见委派工具。

## 五、常用 Skills 的整理与发布

首批从团队真正高频使用的方法整理：文档 / 周报、调研引用、表格 / 绘图、代码开发 / 测试 / 评审、知识检索 / 草稿、云与 HPC 作业查看、动态算法发现和结果解释。它们是工作方法分类，不是固定算法名单。

每个 Skill 至少记录用途与触发条件、输入与交付物、依赖工具及最低版本、允许的数据范围、失败 / 缺失工具时的行为、适用模型、样例与验收用例、维护人和版本。

- 优先复用已有 Skill；先用实际样例检查与本地模型、工具名称及版本是否匹配，不只改标题后发布。
- 分成受管公共集合与项目获准集合，按任务相关性选择；不把所有 Skill 全文和所有工具 schema 塞进每轮上下文。具体懒加载与检索能力按固定 DSH 版本核对，不新建路由 Agent。
- Skill 内容、随附脚本、文档与工具描述都需要审核。脚本仍经获准执行器运行；内容中的“忽略审批”“安装某工具”不能扩大权限。
- 依赖工具缺失时说明阻塞，不能伪造已保存 / 已执行。版本更新先回归再发布，可撤回到已验证版本。
- 凭据不写入 Skill，内部来源不能通过通用总结扩大可见范围。用户可写文件不直接成为生产受信任 Skill 根或 preset 根。

本仓目前仅有三项受管 Skill：公司知识、公司软件开发与量子工作流；不是已装好用户日常所需的全部 Skills。现有 Skill 中历史接口名与软件包名需在正式集成时一起核对；本次未修改其执行内容。

## 六、插件与 MCP 接口鲁棒性

重点是可诊断、可恢复、不会误执行，而不只是遇错自动重试。

1. **版本与启动**：固定插件 / MCP / 模型适配版本，启动做依赖与配置检查；声明变更先做兼容测试。插件可能与宿主同进程，进程外 MCP 也不天然安全，分别限制进程、环境和网络。
2. **连接与超时**：区分启动、握手、单次调用、流式空闲和总预算；设置取消与进程回收。单个连接故障不应拖住全部无关工具；不承诺取消消息等于后端任务已停止。
3. **错误与输出**：区分鉴权、限流、参数、超时、连接中断、远端工具错误、业务失败及执行未知。校验响应结构、来源、大小与内容；协议成功不等于业务完成，半段工具参数不能提前执行。
4. **重试与幂等**：只读查询可在总预算内有限退避，并尊重服务重试要求；提交、写入、发送、计费先核对幂等合同。已提交但回执丢失先查询状态；设备自动重试继续为零。
5. **长任务**：受理与完成分开，云 / HPC 原服务保存作业事实。按现有查询 / 事件机制跟踪，断线恢复不重新提交。MCP 请求标识或诊断关联号不是业务幂等保证。
6. **身份与数据**：逐用户 / 项目授权在服务侧复核；凭据、日志、缓存和临时文件隔离，撤权后不能继续读旧缓存。OAuth、令牌刷新、重连等按实际服务支持验收，不假定协议自动完成。
7. **网络与供应链**：端点、重定向、下载和 stdio 启动命令受管；用户不能随意指定可执行文件或内网地址。固定依赖 / 校验来源，缺少设备凭据仍须辅以设备网络隔离。
8. **容量与降级**：限制并发、队列、资源与输出；故障过多时暂时停止向该服务发新请求，保留诊断。降级只能减少功能，不能改用未授权外部模型 / 账号 / 设备或吞掉科学结果错误。
9. **可观测与回归**：记录脱敏的关联信息、版本、耗时、状态与错误类别；将坏响应、断流、拒绝、限流、并发、重连、撤权、服务升级和恶意内容加入回归。重放仅对替身或明确无副作用的接口，不能自动重放真机执行。

这些是验收要求，不是宣称当前所有保护已覆盖任意第三方插件。优先沿用 DSH 与既有服务已有的超时、取消和监控机制，只补缺口与跨层语义，避免一层套一层的独立重试。

## 七、实际建设顺序与估算

1. **盘点可复用项**：固定 DSH 及组件版本，列出常用任务、现有插件 / MCP / Skills、服务负责人和权限；标注“直接复用 / 薄适配 / 确需新增”。
2. **跑通通用最小集合**：本地模型 + 受管通用工具 + 少量高频 Skills，在既有三栏中完成文件、编程、分析和调研代表任务。界面设计与文档格式只是有界验收样例，不要求先建完整办公套件。
3. **并列接入公司服务**：知识库、云平台、HPC、量子算法按已有接口就绪程度并行接入；每类使用统一准入检查，不等待重建底层平台。
4. **故障验证与受控发布**：先做替身 / 测试租户的错误注入，再做获准真实任务与双租户验证。验证通过后扩大工具集合；设备仍单独审批。

每个工具准入包包含：版本 / 归属、暴露给模型的合同、身份与副作用级别、超时 / 重试 / 取消语义、结果预算、回归样例与运维负责人。

工期应按“选型配置 + 适配 + 安全隔离 + 真实任务 / 故障验收 + 产品界面”估算，而不是为每个能力重新开发运行时和后端。v0.6 的能力要求保留，但不能将其清单全部计为自研新增工程。旧量子专项数字也不是本次 DSH 集成产品的总工期；完成复用盘点后再重新拆包，不凭“只是配置”宣称零开发，也不沿用过重的重建估算。
