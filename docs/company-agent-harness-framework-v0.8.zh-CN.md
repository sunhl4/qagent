## 一、来源与框架命题

框架出自 `~/projects/agent-from-scratch` 工程（学习向 Codex / Claude Code / Cursor / DeepSeek harness 档次的 agent 搭建，全部为文档，未实现）。核心命题：

$$
\text{可完成任务的能力} = \text{模型能力} \times \text{驾驭系统能力}
$$

驾驭系统（harness）是「1 个核心循环 + 8 个子系统」，核心循环为上下文组装 → 模型决策 → 动作执行 → 状态归约；8 个子系统为 S1 模型网关、S2 上下文工程、S3 工具与技能、S4 执行环境与沙箱、S5 状态与记忆、S6 权限与治理、S7 验证与评估、S8 接口与分发。配套 8 条不变量（I1–I8）与 15 种失效模式（F1–F15）。

对公司的含义：**v0.7 的「在 DSH 上做集成」与该框架完全同向。** DSH 已经是这套 harness 的一个实现；公司要做的是把自有约束承载组件接到正确的子系统位置上，而不是新写一个 harness。本文给出逐项对齐、公司应加固的位置，以及对 v0.7 的增量修订。

## 二、8 个子系统 → 公司产品映射

公司代码（`contracts/`、`src/company_agent/`、`packages/`、`profiles/`）对应位置如下。表格回答「该选型 / 该加固 / 该复用」。

| 子系统 | 公司承担位置 | DSH 原生承担 | 公司动作 |
| --- | --- | --- | --- |
| S1 模型网关 | 无（不自研） | 模型适配、流式、归一化 | 只做固定版本核对；本地中文 / 工具调用 / 并发实测属于验收，不属于开发 |
| S2 上下文工程 | `contracts/` 的工具结果预算与内容限制 | 会话与压缩 | **新增**：显式信任分区原则（见四-2） |
| S3 工具与技能 | `packages/` 注册转调、MCP/Skills 准入 | 工具生命周期、MCP 客户端 | 沿用 v0.7 受管装配；补技能适用条件（见四-4） |
| S4 执行环境与沙箱 | `profiles/company-agent/` 受管组合 | 执行能力、隔离机制 | 不开放 shell preset；设备侧保留网络隔离；属长期投入位 |
| S5 状态与记忆 | 云平台 / HPC 作业事实源、知识库入库规则 | 会话持久化 | **新增**：恢复对账与知识来源时效（见四-3） |
| S6 权限与治理 | `contracts/` 策略 + ask/deny + 审计回执 | 权限模式、审批 UI | **公司最大的投入位**（见三） |
| S7 验证与评估 | `tests/` 门禁、验收场景记录 | 无 | **新增**：验收绑定版本四元组（见四-6） |
| S8 接口与分发 | `packages/` 与三栏工作空间 | CLI / UI 原生界面 | 外观只驱动核心循环；官方 Codex 保持隔离外观，不成为第二循环 |

依据框架的耦合点图，S6 是 S3、S4 的前置门：任何公司工具（含 MCP、Skill 引用、普通命令）进入执行前都必须穿过 `contracts/` 策略判定并写入可审计回执。这与现有 hard rules「未知工具、缺失 provider、坏信封失败闭合」一致，只是把它显式化为架构位置。

## 三、投入纪律：约束承载优先，能力承载复用

框架的动态层规律：harness 组件分为两类，随模型能力提升走向不同归宿。

- **能力承载型**（工具调用格式解析、输出格式修复、简单重试、短程检索）：会被模型内化，只做到够用，禁止过度工程。公司对应动作：不在 `src/company_agent/` 重写参数修复、流式解析、协议归一化；这些能力视为 DSH 与本地模型的属性，公司只做固定版本的实测验收。
- **约束承载型**（权限门、沙箱边界、审计回执、预算上限、信任边界）：必须留在 harness，值得长期投入与硬化。公司对应动作：持续加固 `contracts/` 策略、审批与审计、设备 ask/deny、工具结果与内容预算、失败闭合门禁。

因此公司的子系统投入优先级为：**S6 > S4 > S2 > S5 > S7 > S3 > S8 > S1**。落到工程顺序上：合同与策略的硬化先于工具扩容；先扩充 `tests/` 的失效模式反例，再扩插件与 MCP 面积。S1 唯一允许的例外是「验证本地模型能力是否够用」的实测，不是适配层开发。

## 四、对 v0.7 的七项增量修订

### 1. 身份定位不变，新增一层框架职责核对

v0.7 第 一、二 节原文保留。新增核对要求：任何新的公司能力提案，必须先回答它落在哪个子系统、对应哪个能力缺口、遵循哪条不变量；回答不出缺口的能力不进入 `packages/` 或 MCP 准入清单。这替代「功能齐全」式的扩容讨论。

### 2. 信任分区成为显式原则（对应 I2、F4、F5）

框架最重要的安全结论是：上下文中存在两类权威等级完全不同的内容——**可信指令**（系统指令、公司合同、获准 Skill 正文）与**不可信观测**（文件内容、网页、工具输出、知识库正文、邮件），压缩与摘要绝不能把不可信内容提升为指令（压缩洗白）。

对公司的落地：

- 知识库检索结果、云平台页面内容、第三方 MCP 输出、用户上传文件，进入模型上下文时一律按不可信观测对待；它们可以改变 agent 的资料，不能改变 agent 的权限。
- 现有规则「内部来源不能通过通用总结扩大可见范围」「读权限不等于发布权」升级为通用原则：摘要、知识入库、报告生成同样不得提升信任等级。
- Skill 内容审核（v0.7 五）已覆盖技能侧入口；本次扩展到整条上下文链路：任何一段内容若含祈使句式指令，都不能因此获得跨越审批的效力，「忽略审批」「安装某工具」类文本触发失败闭合并记录。

### 3. 恢复必须对账，不静默续跑（对应 I6、F7）

v0.7 六-5 要求断线恢复不重新提交。按框架补齐另一半：会话与工作区也可能漂移。

- 恢复会话时，核对会话状态记录与工作区 / 业务侧实际状态；不一致（用户手动修改、上轮动作未完整落盘、「实际有而状态无」）必须显式报告并由用户选择，禁止静默继续。
- 云 / HPC 长作业恢复以原服务作业事实为唯一真相，agent 状态仅是索引；两者冲突时以作业事实为准并说明差异。

### 4. 工具结果绑定完整执行状态（对应 I7）

框架要求每个工具结果绑定请求、参数、退出码、截断信息、耗时与快照标识；只记录输出文本时，「无输出」「失败」「被截断」无法区分。对公司的落地：

- Python provider 侧 `company-agent-provider/1.0` 信封已有结构校验，继续作为事实标准；本次新增要求：**任何新的 MCP / 插件适配接入同等绑定语义**——受理与完成分开、诊断关联号必须落盘到结果记录，不是临时透传。
- 合同测试同步：新增工具注册时，测试必须包含「异常路径结果仍携带完整状态」的用例，与工具 schema 同步修订（硬规则）。

### 5. Skills 增补适用条件与来源（对应 F13）

v0.7 五的字段要求（用途、触发、输入、依赖、失败行为、样例、维护人）已好。按框架补两项：

- 每个 Skill 声明**适用条件**（前置约束、数据范围、不适用场景），检索装配时校验前置条件，避免「表面相似但约束不同」的任务被误用——与「Skill 不固化算法名单」一致，工作方法是分类而非名单。
- Skill 演化必须有来源轨迹与验证记录；从错误轨迹演化出的处理步骤不得静默成为新版本。版本更新先回归再发布（v0.7 已有），撤回时保持可追溯。

### 6. 验收绑定版本四元组，保证可比（对应 F11、I8）

框架纪律：评测与验收报告必须绑定 harness 版本、模型版本、工具集版本、任务集版本，否则分数不可比。对公司的落地：

- 新增验收报告（含故障注入与真实任务验收）统一记录 `pins.json` 的 DSH 版本 / 组件版本、公司合同版本、本地模型标识与版本、验收用例集标识四项；缺任一项的报告不得用于对比或作为通过证据。
- 既有 `docs/evidence/` 的验收记录沿用，本项从下一次验收开始生效。

### 7. 显式终止与四类预算（对应 I3、I8、F1、F10）

v0.7 六已有超时分类、取消语义、设备自动重试为零。按框架补齐循环侧：

- 任务的终止条件显式化：完成需验证、预算耗尽（token / 墙钟 / 调用次数 / 费用四类中未全部允许时按合同声明）、等待审批、不可恢复，四者终止并如实报告，禁止依赖模型自觉结束。
- 每个动作有唯一关联标识并在执行前扣减预算、执行后写回实际消耗；公司侧关联号已具备，本项纳入后续合同测试的检查范围（本次不改合同）。

## 五、失效模式 → 公司反例与回归清单

框架反例库（F1–F15）优先级「安全 > 正确性 > 稳定性 > 可测性」。映射为公司 `tests/` 与验收门禁的下一次扩充目标：

| 失效模式 | 公司现有防线 | 待补反例 / 回归 |
| --- | --- | --- |
| F4 压缩洗白 | 知识入库来源审核（部分） | 知识 / 文档 / MCP 输出含指令不得越权；摘要不得提升信任（四-2） |
| F5 提示注入 | Skill 审核内容禁令 | 路径三选一以上：文件、网页、工具输出各一条用例 |
| F6 审批绕过 | 合同 ask/deny、失败闭合 | 「绕道达成破坏性操作」类输入必须被拦截并留审计 |
| F7 状态漂移 | 作业事实源规则 | 恢复对账显式冲突处理（四-3） |
| F9 过早宣称完成 | 结果校验 | 无验证证据不声明完成的用例 |
| F15 沙箱逃逸 | 受管 preset、fetch:false | 路径穿越与凭据不进上下文的用例沿用门禁 |
| F2 / F1 / F10 稳定性 | 未知工具失败闭合 | 同类错误重试上限、重复动作检测、预算耗尽终止 |
| F12 / F13 / F14 可维护性 | Skill 审核、门禁 | 记忆 / 知识条目来源与时效；技能前置条件；跨外观一致性 |

本次不新增测试代码；此表作为下一次进入「合同 → Python adapter → DSH 插件 → 测试」时的反例任务清单，先建反例再实现。

## 六、建设顺序的修订

v0.7 七的四步保留，插入两条框架要求：

1. 盘点可复用项时，**同时生成子系统缺口表**：每个候选插件 / MCP / Skill 标注它补偿哪个缺口，避免把同一缺口重复补偿两次（例如插件与 MCP 各配一份重试编排）。
2. 鲁棒性验证（原第 4 步）在错误注入之外，**加入 F4 / F5 / F6 三条安全反例的验证**（可用替身内容注入）；设备专项验收仍单独进行。

四类预算与终止条件（四-7）在跑通通用最小集合时就要生效到验收用例中，不等全量启用。
