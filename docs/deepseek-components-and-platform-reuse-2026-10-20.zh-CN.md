# DeepSeek 官方开源组件选型：成熟云平台与 HPC 前提

初版日期：2026-10-20；前提更新：2026-10-21 08:43（UTC+8）。依据：用户确认云平台和 HPC 平台均已成熟，并补充公司已有本地部署的大模型及 DeepSeek；开源组件说明仍依据 2026-10-20 查阅的官方仓库与模型卡，本次未重新核验上游版本。本文为选型与集成建议，没有安装组件、升级 DSH、读取凭据或连接设备。

> **本次补充：模型能力也按既有服务复用。** Agent 的模型工作是接口接入、权限和数据边界、工具调用及任务行为验收，而不是重新训练模型、采购算力或更换推理引擎。具体 DeepSeek 型号、服务部署范围与协议尚未给出，不从“已有 DeepSeek”推断为某个版本或已通过 DSH 工具调用验收。

## 一、结论与定位修正

**最值得用的是 DSH 的既有扩展机制、文档解析能力，以及与实际模型匹配的协议适配；底层推理、通信和存储组件按瓶颈选择，不为采用同一品牌而整体替换成熟平台。**

既有系统的责任保持明确：

- 量子云平台：账号、项目、资源权限、任务状态、结果服务、计量和账本等既有能力。
- HPC 平台：经典资源、作业排队、配额、运行环境、存储与运维等既有能力。
- 既有本地大模型 / DeepSeek 服务：提供模型推理；服务运维沿用现有团队与部署，DSH 通过受管模型适配接入，不另建模型或工具循环。
- Uniqon：科学计算框架、动态能力目录、科学结果 / 预算语义；它的本地验证状态不能代表公司云平台或 HPC 平台成熟度。
- Company Agent + DSH：自然语言交互、可信工具调用、审批呈现、项目工作空间和短结果解释。
- 文档解析 / 检索 / 分析：独立数据服务，保持来源、权限和可复现性。

不再以“云平台和 HPC 要从零建设”或“公司还要部署基础大模型”作为默认前提。仍需对齐的是 Agent 接入点和业务语义，而不是重新实现既有平台或模型服务。

## 二、优先级最高：把 DSH 已有扩展能力用好

### 2.1 界面、会话事件与模型适配

官方 DSH 架构提供模型 adapter、工具注册、会话持久事件、流式呈现、界面扩展与会话存储替换接口。它与用户提出的右侧对话、审批卡、任务引用和业务内容展示直接相关。[D1][D2]

建议：

1. 右栏复用既有 DSH 会话 / 流式机制；审批按当前受管策略展示。
2. 三栏工作空间的项目、任务列表、账单、文件和结果直接消费云平台 API，不经模型查询每一行。
3. 任务卡、报告引用和审批卡用受控界面组件接入；不要把生成 HTML 的任意脚本放进主站权限域。
4. 会话事件是交互记录；云作业事件仍以云平台为事实源。DSH 的本地 background jobs 不是量子云 / HPC 调度器。
5. 现有成熟平台 API 优先经过项目合同与 provider adapter；即便平台另提供 MCP，也不能把发现的工具绕过合同自动暴露给模型。

**版本限制：** 本仓 `pins.json` 固定 DSH `0.1.5-rc.2`。本次查阅的是上游当日文档，不证明所有新扩展点都已包含在当前锁定版本。应选择必要能力做版本差异和兼容测试，不直接整体升级。

**安全限制：** 官方 `SAFETY.md` 明确 DSH 是 developer preview、未经安全审计，不能作为不可信负载的唯一安全控制。这不取消本仓的既有防护，但意味着外部租户仍需平台级身份验证、进程 / 容器隔离、最小权限和受控发布。[D3]

**不采纳的默认项：** 官方示例中的 shell、任意代码执行、定时自主调用、动态 workflow、用户可写 preset 和模型可见委派工具，不因“上游提供”而进入生产。继续遵守 DSH 唯一运行时、受管组合、Codex 隔离与设备逐次审批硬规则。

## 三、优先试点：DeepSeek-OCR / DeepSeek-OCR-2

**适用价值：** 光学字符识别（OCR）可用于扫描版论文、设备手册、图片型 PDF、内部实验记录等的知识入库预处理。官方 OCR-2 提供图像和 PDF 推理示例，以及文档转 Markdown 的模式。[D4]

建议入库流程：

原文件受控保存 → 优先抽取已有文本层 → 对扫描页或布局失败页执行 OCR → 记录页码 / 来源 / 解析版本 → 表格、公式与关键字段核对 → 继承权限入索引 → 需要共享发布时再审核。

关键边界：

- QASM、代码、JSON、CSV 和设备返回的结构化结果用原生解析器处理；不先截图再 OCR。
- OCR 是提取器，不是完整企业知识库。它不提供文档权限、检索、引用正确性、版本撤回和知识发布审批。
- 论文公式中的上下标、负号、单位、矩阵顺序、表格列对齐都可能识别错误；不能用通用识别分数替代量子领域验收。
- 电路图片识别不能直接转为可提交真机的可靠线路；图形理解产物仍须结构与语义校验。
- 输出是未可信参考数据，文件中的指令不授权工具行为。页码等来源元数据由入库服务显式绑定，不假设 OCR 自动正确生成。
- 官方 Transformers 示例使用 `trust_remote_code=True`；生产固定模型和代码 revision，审核后离线部署到独立环境，不在 Agent 进程里动态装载远端代码。

**何时值得做：** 如果内部材料大量是扫描 PDF / 图片，优先级高；如果主要是 Markdown、源码和有文本层的 PDF，先完成授权索引，OCR 只作补充。

**小试点建议：** 选取已脱敏且获准的代表性文档页，覆盖中英混排、公式、跨页表、双栏论文和扫描噪声；比较原生抽取与 OCR 路径，记录字段正确性、可追溯引用、失败率、延迟和资源成本。不在试点前宣称固定压缩倍数或识别精度。

许可范围：官方模型卡元数据标注 Apache-2.0；此次尝试读取 GitHub 根 `LICENSE` 返回 404，因此代码、模型权重、依赖和分发义务仍分别确认，不以模型卡代替全部许可证清单。[D5]

## 四、按本地模型适配需要采用：deepseek-recipe

**作用：** 官方将其定义为 Rust 库及 Python bindings，用于 Messages / Chat Completions / Responses 格式转换、DeepSeek V4 / V4.1 提示格式与 token 编码、推理输出和工具调用解析。[D6]

**为什么可能有用：** 自建推理服务如果缺少兼容协议、流式工具参数或正确提示模板，可以减少自行实现这些格式的工作。它应位于模型服务 / 协议网关，不进入科学算法包，也不创建新的 Agent 工具循环。

**什么时候不用：** 已有推理服务若正确支持 DSH 需要的接口和流式工具调用，不必为了增加组件再包一层。实际模型未确定时，也不能默认这些 V4 / V4.1 格式适用于全部 DeepSeek 或其他模型。

**明确缺失：** 该库不提供模型推理、HTTP 传输或工具执行；结构化 schema 的提示 / 约束声明也不代表推理后端一定实施了约束解码。权限、审批和参数校验仍在 Company Agent 与平台服务端。

**网络风险：** 官方说明图像 URL fetcher 默认可访问任意地址；处理不可信请求必须配置目的地址限制，防止访问内网敏感接口。优先使用授权资产通道传输图片。

代码与公开文档官方声明 MIT；tokenizer 和第三方依赖通知另核。[D6]

## 五、交给推理平台团队按瓶颈评估的组件

### 5.1 DeepInfer：有条件的后端候选，不是首期必须更换的服务

本次官方 README 声明支持 DeepSeek-V4.1-Flash、NVIDIA SM100 与 Huawei Ascend 950，公开交付范围为 offline inference。完整在线服务还需要 KV cache 系统、分离式推理服务组织与副本负载均衡等部件。[D7]

因此，“官方用于生产服务的技术”不等于“公开仓库拿来就是完整生产在线 API”。若现有推理服务工作良好，先继续使用；只有模型、硬件、并发与收益都匹配时才做独立压测。支持范围随上游变化，实施时固定版本。代码官方声明 Apache-2.0，模型权重许可另核。

### 5.2 DeepGEMM：矩阵计算内核

主要优化大模型矩阵乘法、混合专家（MoE）相关计算等；当日 README 的 NVIDIA 路径要求 SM90 / SM100 等特定软硬件组合，昇腾有独立仓库。[D8]

用途是推理 / 训练后端优化，不是直接给量子算法或 QPU 加速。FP8 / FP4 等精度与布局选择也不能直接替代科学计算所需数值精度。优先通过推理引擎已有集成使用，不在 Company Agent 中 import。

### 5.3 FlashMLA：注意力内核

当日主分支明确提示 2026-09-30 版本移除 Hopper 与部分前代模型支持，改变 KV cache 格式；旧模型或旧硬件需要对应历史版本。[D9]

因此不能沿用“FlashMLA 一律适合某种 GPU”的过时说法。先确定模型、GPU / NPU、框架、CUDA / CANN 和精度组合，再确认兼容性与端到端收益。

### 5.4 DeepEP：模型内部通信，不是量子资源调度

它主要提供 MoE 专家并行 dispatch / combine 等 GPU 通信操作；当日版本还含标记 experimental 的其他并行通信功能，对网络与运行库有明确要求。[D10]

只有多卡 / 多节点模型推理或训练的通信确实是瓶颈时才有价值。成熟 HPC 可以承载它，但它不能替代已有作业调度器，不能解决 QPU 队列、量子线路映射、离子时序或跨资源审批。

### 5.5 DeepJIT、TileKernels 等

可作为上述推理栈的依赖或底层优化工具，通过维护该推理栈的团队评估。当前 Agent 产品不需要单独维护一套 kernel 开发工程；不因引入更多底层库而假设获得固定性能提升。

## 六、你们现阶段通常不应优先替换的组件

### 6.1 3FS

Fire-Flyer File System（3FS）是面向训练 / 推理负载的分布式文件系统，涉及 SSD、RDMA 网络和元数据基础设施。[D11]

已有成熟存储和 HPC 时，先复用。只有实测出现数据读取、训练检查点或推理缓存的存储瓶颈，且平台团队愿意承担迁移与运维成本，才另立基础设施评估。

**3FS 不是知识库，不自动提供租户资料授权、检索、来源审核或公司数据治理。** 不为 Agent 工作台上线引入一次存储替换。

### 6.2 smallpond

它是基于 DuckDB 和 3FS 的数据处理框架，可作为大规模离线数据整理、聚合和质量检查的候选。[D12]

在已有 HPC / 数据处理系统成熟的条件下，属于数据平台团队的可选工具；不是聊天数据库、向量检索系统或量子结果语义验证器。官方规模基准不能外推到公司数据和硬件。

### 6.3 DualPipe

它是针对大模型训练计算 / 通信重叠的流水线并行算法，真实应用还需要按具体模型实现相应计算重叠。[D13]

没有自研大模型训练计划时，通常不是当前优先事项。训练流水线调度不等于 HPC 与 QPU 的作业协同，更不能作为实时设备控制器。

## 七、既有本地大模型与 DeepSeek 如何接入

### 7.1 以现有服务为首期模型入口

2026-10-21 用户补充公司已有本地部署的大模型和 DeepSeek。首期从组织允许使用的既有服务中确定一个默认模型，先打通受管任务；有实际需要时，再通过同一 DSH 的既有模型适配机制增加其他获准模型。DeepSeek 模型服务与 DSH（DeepSeek Harness，Agent 运行时）是不同层，已有前者不等于本项目已完成后者的接入。

- **推理服务**：产生文本和工具调用建议，沿用现有部署及运维。
- **DSH**：承担唯一会话、模型交互和工具调用生命周期；模型配置继续复用其机制。
- **Company Agent 与业务服务**：独立校验工具、参数、权限、审批、预算和结果，不把模型的判断当授权凭证。
- **知识与结果服务**：提供按权限检索的引用与短摘要；完整科学数据经受控文件 / 结果通道展示。模型解释实际结果，不代替科学计算与验证。

本地部署有利于控制数据流向，但不自动获得公司全部知识，也不自动实现租户隔离。上下文、检索、模型网关日志与缓存仍需按组织 / 项目授权和保留策略处理。内部源码和客户数据仅送到获准目的地；本地服务故障时，不默认回退到公网 DeepSeek 或其他外部模型。

### 7.2 剩余工作是接入与任务验收

先取得非敏感的服务说明：可用模型及版本、接口协议、鉴权方式、流式工具调用支持、上下文限制、并发 / 限流和日志保留策略。访问地址与凭据按公司受管渠道配置，不需要在对话中提供密钥。

验收覆盖中文需求理解、动态能力目录查询、工具参数校验、拒绝后的行为、未知执行不重跑、引用和结果解释、流式中断 / 取消，以及双租户并发隔离。普通聊天可用，不代表上述行为均已满足；如模型不适合工具任务，可继续用于获准的问答和摘要，不以开放 shell 或绕过审批补偿。

本轮优先确认接口协议与工具调用能力即可；GPU / NPU 和推理引擎细节只在发现兼容或性能问题后由推理团队核对，不再把底层硬件选型列为 Agent 方案的前置问题。

### 7.3 开源组件采用顺序随此前提收敛

- 已部署且满足接口要求的模型优先复用；不另行部署模型来凑齐组件。
- deepseek-recipe 仅在现有协议存在具体缺口、且模型版本受支持时评估。
- DeepSeek-OCR-2 是扫描文档解析的独立需求；已有 DeepSeek 对话模型不代表已具备 OCR 服务，也不构成必须安装 OCR-2 的理由。
- DeepInfer / DeepGEMM / FlashMLA / DeepEP 保持后置，由现有推理团队在实测瓶颈下决定。

模型评测排名不能代替公司任务验收；R1 及蒸馏版本只在现有可用服务与任务需要匹配时作为候选，不从“DeepSeek”品牌推断版本或能力。模型权重、代码、蒸馏底座与依赖许可逐项确认，例如 R1 仓库列出的 Qwen / Llama 蒸馏来源差异。[D14] 不为迎合模型示例删除安全系统指令。

## 八、建议的首期组合

1. **保留成熟平台**：云平台与 HPC 是权威执行 / 资源 / 费用系统。
2. **复用 DSH**：只启用受管的模型、会话、事件、工具和必要界面扩展；项目当前合同仍是工具真源。
3. **模型服务保持稳定**：优先用已部署服务；有协议缺口且模型受支持时评估 deepseek-recipe。
4. **文档解析按需增加**：原生文本解析为主，OCR-2 处理扫描与难解析页面，再进入授权检索。
5. **分析服务独立**：公司数据 / 绘图模板计算指标，DeepSeek 解释短摘要；图表不依赖模型编造数值。
6. **底层优化后置**：DeepInfer / DeepGEMM / FlashMLA / DeepEP 只在可测瓶颈和兼容性明确后进入独立评估，不进入首期关键路径。

## 九、既有平台与模型前提下的工期

用户确认的平台成熟度和已有模型服务作为当前规划前提接受；尚未核验的是 Agent 所需 API、模型工具调用、委托授权、设备审批绑定与结果 / 计费语义的对接，不再质疑或重复建设既有平台与模型服务。

**2026-10-21 补充不再重复扣减工期：** v1.1 工作包 D 已是“本地模型接入与行为评测”3–5 人周，没有计算基础模型训练或从零研发推理引擎。v1.2 明确沿用现有部署，保持该工作量及以下总区间；接口直接兼容、行为验收通过后可据实收窄，而不是因“已有模型”再机械减半。以下估算仍针对原定量子工作空间有界范围。2026-10-21 09:33 明确 [v0.7 DSH 插件 / MCP / Skills 集成路线](company-agent-dsh-integration-v0.7.zh-CN.md)，优先复用通用能力和公司本地模型，公司服务并列接入。原数字只作量子专项参考，不能代表当前产品；需先盘点复用与适配、补齐接口鲁棒性，再去重估算，不能将每项通用能力都当作待自研子系统。

沿用六名专职工程师、70% 有效投入以及 20%–30% 风险准备：

- 模拟试点：**9–15 周**，工作量 29–47 人周，风险后 35–62 人周。
- 受监督真机与计费试点：**累计 12–20 周**，工作量 39–62 人周，风险后 47–81 人周。这一档与上一版已列的成熟平台情形一致。
- 有界较完整首版：**累计 28–50 周**，工作量 94–156 人周，风险后 113–203 人周；新增科学研究、硬件开发和无人值守设备不包含。

v1.1 相对 v1.0 主要减少现有工作包 B/F/H/I/J 的平台建设或治理补建部分，保留适配 / 联调 / 验收；后续 N/Q 减少重建 HPC 和通用运维工作的估计。界面、结果语义、分析模板、内部知识授权和新设备审批仍需开发，因此不机械将总工期减半。

这些是有条件的规划值，不是已经验证的团队速度；具体接口若直接可用可取区间低端。v1.2 只记录既有模型前提与范围澄清，不改变数值。引入新的推理栈或替换存储反而可能拉长工期，所以没有给开源组件额外记一笔未经实测的“自动提效”。
