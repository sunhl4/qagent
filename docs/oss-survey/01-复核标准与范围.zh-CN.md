# 开源调研复核标准与范围

复核日期：2026-10-22。范围是原清单的 **57 个独立项目**，按编号 01–57 对账；附属仓库、改名仓库和拆分后的规范仓库不重复增加数量。

## 1. 这次要解决什么

此前文档同时出现“61 个”“57 个”“深读 48 个”等不相容统计，且把 19 项清单速评计入深度调研完成。旧稿还混淆源码中的机制、未运行的能力、产品部署和工程建议。本轮以逐项目复核稿替代旧稿结论，不以文档数量冒充项目完成数。

`reviewed/projects.json` 固定研究对象；`reviewed/evidence-*.json` 记录各项目实际源码版本及证据。完成数只能从独立编号计算。此前已有稿的 38 个项目也要重审，不能因为有文件就免审。

## 2. 单项目完成条件

每个项目必须同时交付：

1. 独立中文复核文档，标明研究对象、获取到的仓库、完整 Git 提交 SHA 和提交时间。
2. 许可证原文来源与适用目录；不同模块许可不同则分别记录，避免把“公开源码”当成“可任意再分发”。
3. 至少一条完整调用链及关键函数分析，覆盖输入验证、权限或隔离、执行、输出或持久化和失败行为中的实际适用部分。
4. 至少三个实现证据锚；规范或技能仓可以用规范、脚本、校验器代替服务端实现。
5. 至少一个测试证据锚，说明测试实际断言了什么。确无测试的仓库需明确记录，并用可执行检查器或规范示例说明验证缺口，不能伪造测试文件。
6. 至少六个文件与行号证据锚，含许可证；引用必须针对记录的 SHA，不能只链向会变化的默认分支。
7. 至少一段短的逐字源码/规范引用；省略或转述的文字放在引用外，不伪装为源码。
8. 对 Company Agent 的具体适用边界及文件落点；区分可直接候选、仅借机制、暂缓、不符合本项目硬规则。
9. 明确验证级别。本轮默认是“静态源码及测试阅读”，不声称已跑通上游测试、已经生产接入或达到商业交付标准。

对某一功能证据不足，结论应收缩到实际读到的代码；不能用“目录存在”“名字相似”“README 提到”证明它已满足我们的完整要求。

## 3. 复核的架构约束

- DeepSeek Harness（DSH）仍是唯一 Agent Runtime；协议 SDK、测试驱动器、遥测出口不自动成为第二运行时，但任何生产模型/会话/工具循环都不能另起一套。
- `contracts/` 是公司工具和策略真源。发现期过滤、前端按钮、MCP 注解和 Skill 说明都不能代替执行期授权。
- `quantum_device_run` 在 `lab`、`sign` 必须人工确认，在 `boot`、`algo` 必须拒绝；变更参数不能直接复用旧批准。
- 算法目录从平台 `algorithm.catalog` 动态取得，标识仍是平台 `component_id`；本调研不把任何算法名单固化进 Agent。
- 资源句柄只有 `asset_id`、`circuit_id`、`twin_id`。只有绑定 `ionstack-twinrun` 的 `quantum_device_run` 能产生 `twin_id`，它不是容器、检查点或普通任务的通用句柄。
- 现有公司本地模型、云平台和高性能计算（HPC）平台都是前提。调研 Ollama、vLLM、LiteLLM 不等于决定迁移部署。
- 生产环境不能通过可写 preset、shell 或对外暴露的 Codex 委派工具绕过权限。
- 科学正文、凭据和全量电路不因“写审计”“做摘要”而获得豁免。评估工具也不能默认把内部信息发往外部生成/遥测服务。

## 4. 许可证与活跃度的正确口径

源码许可分析只是工程选型初筛，不是法律意见。AGPL 有相应义务，不能笼统写成“公司硬规则禁止”；有品牌条款也不能直接推断“所有修改都必须购买企业许可”。商业模块的功能归属需要具体文件或调用证据。

还要区分“原清单57个候选”与“当前57个都仍为维护中的开源实现”。例如 Daytona 当前 README 明示核心迁入私有代码库，复核需要固定公开历史标签；不能把私有最新版当作已读源码。

提交时间只证明这份快照的时间；`git ls-remote` 只列远端引用。没有仓库归档标记、维护者声明等证据，就不写“停推”“停止维护”。版本号、SHA、维护状态和部署可用性是四个不同概念。

## 5. 本地检查与交付边界

文档检查验证项目编号唯一性、证据文件存在、行号范围、SHA 一致、引用内容一致，以及旧入口是否指向新稿。该检查不能证明源码没有安全问题，也不能代替上游测试和公司真实环境验收。

本轮只更新调研文档与文档校验工具，不修改公司工具合同、Python 业务适配器、DSH 插件或生产配置，不连接云平台、HPC、QPU 或本地模型，不读取账号密码或令牌。
