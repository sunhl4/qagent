# 公司现有实现与调研建议的边界复核

日期：2026-10-22。此文是对当前工作区代码的静态核对，不是一次真实服务连通性或生产安全验收。本轮不修改合同和运行配置。

## 1. 主结论

公司已经具备合同、策略、工具注册、结果限制和诊断链路。外部项目的价值应落在现有结构的缺口上，而不是重新建设一套 Agent、模型网关、账号系统或作业调度器。

此前“新增审批策略文件”“新增工具输出预算”等说法忽略了现有代码。应先区分三类：现有能力及其测试、需要进一步验证的运行性质、尚未实现的产品级需求。

## 2. 审批策略已经在合同内，不从通配符重新起步

`contracts/policy.json` 已声明设备工具、provider、ask/deny preset，且还声明 HPC 提交的审批边界。

```5:9:contracts/policy.json
  "device_tool": "quantum_device_run",
  "device_provider": "ionstack-twinrun",
  "device_provenance": "qccd-twin",
  "device_ask_presets": ["lab", "sign"],
  "device_deny_presets": ["boot", "algo"],
```

`src/company_agent/policy.py` 的 `decide()` 校验工具是否登记、preset 是否已知、工具是否可见，以及合同中的设备/提交策略是否满足硬规则。`tests/test_policy.py` 已包含未知工具、未知 preset、畸形合同、设备身份错配和设备必须人工确认的用例。

因此，inspect_ai 的 glob 审批策略只是对照机制，不应替换已有严格工具名映射。`modify`、`escalate` 也不能直接扩充公司三态权限模型：审批者修改参数后，原授权范围是否仍有效必须重新核对；设备不能因模型判低风险或“总是允许”而免审。

建议的增量是检查审批关联与参数不可变性、拒绝后不派发、断线重入不复用错误批准。具体测试应先对照 `tests/test_plugin_policy.py`、`tests/test_dsh_lifecycle.py` 和 `tests/test_plugin_runtime.py`，不能先宣称这些能力全都缺失。

## 3. 结果限制已经存在，且科学结果不能静默裁剪

```2:9:contracts/results.json
  "version": "2.0.0",
  "output_content": {"scope": "all_tools", "known_credentials": "reject_echo", "reference_trust": "untrusted_reference_data", "max_safe_integer": 9007199254740991},
  "max_result_bytes": 64000,
  "provider_result": {
    "max_depth": 8,
    "max_mapping_items": 64,
    "max_list_items": 32,
    "max_string_bytes": 4000,
```

当前总结果上限是 **64,000 字节**，不是 64 KiB；字符串、列表、映射和嵌套还各有上限。它是现有合同事实，不代表未来不能调整，也不代表换成更小数值就能解决所有内容风险。

`src/company_agent/sanitize.py` 区分内容校验、总大小校验、provider 数据的禁止字段检测及防御性短结果函数；`has_forbidden_output()` 明确拒绝会有损的 provider 数据。`invoke.py` 在返回成功前依次验证内容、句柄、输出 schema 与总大小。插件 `runtime.js` 的 `validateInvocationResult()` 与输出渲染也有字节检查。

因此，inspect_ai 的 16KB 默认截断只能用来比较机制，不能直接覆盖本合同。模型输入上下文截断、生成 token 上限、provider 响应体上限、工具结果上限和遥测入库上限是不同边界。

建议的增量：若未来需要大结果，应由平台保存并返回现有类型的授权句柄与可验证摘要；明确完整性、分页和拒绝原因，不能把科学数组静默截短后标成功。

## 4. 严格信封已经存在，宽容解析属于测试端而非生产边界

`invoke.py` 的 `_validate_arguments()` 使用合同 schema，拒绝未知字段；`validate_invocation()` 拒绝未知工具、无效工具名和非 JSON 对象。插件 `runtime.js` 的 `authorize()`、`validateInvocationResult()` 对字段集合及状态组合再次校验。

因此，promptfoo 为生成攻击样本提供的多字段别名、JSON 修复不能迁入公司生产调用入口。测试端可以生成畸形信封；生产端的期望结果仍是拒绝并记录，不能把输入“修好”后擅自执行。

`tests/test_contracts.py` 已验证合同图闭合、provider 操作覆盖、preset 可见性以及工具只注册一次。GitHub MCP 的快照方式可作为补充，但不应另维护一份与 `contracts/tools.json` 分叉的工具清单。

## 5. 诊断与执行状态已有基础，遥测仍不等于合规账本

`contracts/results.json` 已列出诊断字段和 `not_dispatched`、`dispatched`、`completed`、`unknown` 四种执行状态。`diagnostics.py` 只输出白名单元数据，写入 stderr；写诊断失败返回 `False`，不会伪造或覆盖已经发生的执行结果。

这意味着“已有诊断”可以确定，“已有持久、完整、防篡改的审批审计账本”不能仅据此确定。Langfuse、Phoenix 或 OTel（OpenTelemetry，遥测标准）可以消费关联信息，但采样、异步队列和失败丢弃都需要单独设计；trace 不自动承担计费凭证、权限判断和业务事实源职责。

建议的增量：决定哪些执行前记录必须可靠持久化、哪些运行后事实需对账补记，以及观测出口故障时的策略。不能在 QPU 已执行后因为遥测失败把结果谎报成“未执行”或自动重试。

## 6. 外部作业恢复不等于 Agent 检查点恢复

```24:25:contracts/results.json
  "device_execution": {"automatic_retries": 0, "request_id_is_idempotency_key": false, "uncertain_failure": "unknown"}
}
```

合同明确：设备自动重试为零，`request_id` 不是幂等键，不确定结果标记为 `unknown`。LangGraph checkpoint、Durable Object、Git 工作区快照等可以恢复对话和本地状态，但不能撤销已提交的量子或 HPC 作业，也不能保证外部服务 exactly-once。

正确恢复顺序是：按已有业务关联查询云/HPC/QPU 事实，比较本地索引，再给用户解释差异；只有平台明确支持的幂等语义才可用于重提。`asset_id`、`circuit_id`、`twin_id` 的所有权保持不变，不把 checkpoint ID 或容器 ID 冒充成 `twin_id`。

## 7. 账号、可见性与计费分开验收

`invoke.py` 的 `_capability_payload()` 按 preset 计算 `visible_tools`，且 provider 配置通过时明确返回 `configured_unverified`，不是“已联网可用”。`contracts/presets.json` 是工具可见性组合，不等于完整企业租户授权系统。

对用户原始问题，要至少分别验证：账号登录成功、服务开通获批、运行环境拿到托管凭据、当前会话注册了对应工具、执行期获授权、实际探测成功。任何一层不能由另一层的绿色状态代替。

进一步核查 `apps/company-workspace/host.mjs:111`，`planOpen()` 以全局云 key 或 HPC 用户/主机配置是否存在计算开通状态；`:354-403` 的申请/批准流程写入本地请求集合，批准按服务种类处理 pending 请求。这可服务本机演示，不能仅据此宣布企业级逐用户/租户开通与隔离已经完成。该观察不等于当前存在可利用越权：请求还经过独立 gate，本轮没有做运行攻击验证；它说明 Open WebUI/LibreChat 等授权模型有明确可对照的产品缺口。

公司云平台和 HPC 已成熟：其资源配额、作业事实与账单仍应是权威来源。LiteLLM 的模型 token/cost 预算适合模型调用维度，不能直接代替 QPU shots、HPC 节点时、服务开通和最终结算。

## 8. 建议的工程次序（未在本轮实施）

1. 合同层先明确新接口确实补哪个缺口，保留当前 fail-closed、句柄和设备策略不变量。
2. Python adapter 侧补充身份/租户、持久回执、外部作业对账或分析模板需求时，再定义对应 provider 能力；不直接 import 科学算法包。
3. DSH 插件只注册并转调，工作台订阅白名单事件；不引入第二会话循环，不把前端 state 视为服务端权限。
4. 同步合同和注册测试，增加真实环境验收；每项验收绑定 DSH、模型、工具合同、任务集版本。
5. 通用文件、代码、网页和 Skills 能力的扩容必须有受管执行边界，不能借安装别家框架或切换带 shell 的 preset 绕过生产限制。
