## 1. 接入原则

DeepSeek Harness（DSH）承载唯一 Agent 运行时；公司负责合同、授权、短结果、外部作业对账和产品工作台。MCP 是工具接入协议，Skills 是受管工作指令，两者都不是独立授权系统。

从 57 个参考项目里选择组件不等于把 57 个项目全部安装。一个需求已有公司平台或 DSH 提供时，应优先验证现有能力；只有明确缺口再引入依赖。引入的版本、许可、出网行为、数据访问范围和撤回方式都要登记。

## 2. P0：让“可见、可用、已执行”分别有证据

### 2.1 统一能力与连通性状态

**现有基础**：`invoke.py` 将 provider 配置存在标记成 `configured_unverified`，preset 有各自 `visible_tools`，这是合理区分。

**需要的产品闭环**：账号已登录、服务已开通、托管凭据已注入、当前会话有工具、执行期获授权、探测成功分别展示。探测证据应带时间、版本和错误分类，过期不能继续当“在线”。云/HPC 页面可打开不等于对话具备提交工具。

**文件落点**：先审 `contracts/capabilities.json`、`contracts/providers.json`、`contracts/tools.json`；再审 `src/company_agent/capabilities.py`、`providers.py`、`invoke.py`；再将白名单状态同步到 `packages/` 和 `apps/company-workspace/`。

**验收反例**：账号开通但工具未注册；工具已注册但 provider 缺失；凭据有效但无资源配额；旧会话工具集未刷新；浏览器登录成功但后台认证失效。各场景要返回各自状态，不能统一误报“平台不在线”。

### 2.2 审批关联与结果不确定性

**保留**：设备在 `lab/sign` 必须 ask，在 `boot/algo` 必须 deny；已有 HPC submit 合同也不得放宽。

**验证**：批准绑定调用、参数和主体；审批等待超时、参数改变、断线恢复、并发调用不能串用批准。上游框架的“修改参数后批准”“总是允许”“云端自动批准”都不是默认兼容路径。

**文件落点**：`contracts/policy.json` → `src/company_agent/policy.py`、`invoke.py` → `packages/company-agent-policy/`、`company-agent-core/src/runtime.js` → 现有策略与生命周期测试扩展。

**验收反例**：过期批准、重复批准、跨用户批准、批准后参数变化、未知工具加到可见列表。所有拒绝必须在业务派发前发生。

### 2.3 回执持久性与外部作业对账

**现有基础**：白名单诊断、合同 digest、请求关联、执行状态、设备零自动重试。

**需确认的缺口**：诊断输出是否有可靠保存、身份归属、保留策略和对账入口。观测系统不是这些要求的自动实现。

**事实源**：队列、运行、完成、取消和费用以云/HPC/QPU 平台为准；Agent 会话只存引用及对账状态。超时后 `unknown` 不等于平台失败，更不允许静默重提。作业被取消的请求受理与实际取消完成也要区分。

**验收反例**：平台受理后回包丢失；会话恢复但作业已完成；用户手动取消；遥测存储不可用；同一 UI 动作重复发送。每次都核对平台事实，不依赖 checkpoint 自动回放副作用。

## 3. P1：结果回收、分析模板和知识库

### 3.1 保留科学结果的完整性

公司合同已有短结果上限和禁止内容规则。新增分析模板应定义输入来源、schema 版本、单位、完整性状态、错误行为和权限范围。模板输出是授权摘要、指标及受管图表，不把完整 QASM、bitstrings 或敏感校准信息塞进模型结果或遥测。

借鉴结构化输出机制时仍需业务校验：符合 JSON schema 不代表指标单位正确、数值合理、调用被授权。保存大产物使用现有平台资产语义，不能发明新的模型可见句柄类型。

**文件落点**：`contracts/tools.json`、`results.json` → provider adapter 与 `sanitize.py`、`invoke.py` → 插件输出 schema → schema、metrics、句柄与结果测试。

**验收反例**：缺列、单位错配、NaN、概率越界、超长科学数组、恶意文件名、跨租户资产 ID、图表声明包含外部脚本。

### 3.2 知识入库不是默认记忆写入

采用“解析→分块→来源/权限标注→索引→检索后复核”的流程即可起步。向量、图谱和自动记忆抽取是候选实现，不要求一次引入三个存储系统。

**边界**：检索前过滤租户与用户权限，结果物化与导出再次核对；摘要不能提高原文的信任等级和可见范围。知识条目记录来源版本、有效期、撤回状态及入库审批。平台算法目录仍动态读取，不由知识库代替。

**验收反例**：内部文档被公共摘要引用；撤回文档仍命中旧索引；用户 A 的记忆影响用户 B；网页注入变成系统指令；源文档更新但图谱/向量未同步。

### 3.3 Skills 准入与生命周期

保持标准 SKILL.md 元数据和按需加载，补来源、依赖、适用范围、脚本审查与撤回记录。脚本与 hook 是可执行内容，安装技能不自动授权执行。

**文件落点**：现有 `skills/` 与受管 `profiles/`，搭配准入记录和发布回归；不把供应商目录或远程 registry 自动变成生产信任源。

## 4. P1：可重复的验证体系

- 确定性门禁负责未知工具、坏信封、句柄、权限、单位、结果预算和敏感内容；模型判分不能覆盖这些红线。
- Promptfoo、Inspect、SWE-bench、simple-evals 等可用作测试面参考，不能进入生产对话循环。测试生成与裁判模型使用内网批准的端点；禁用不需要的遥测/外部生成。
- 测试集覆盖正常任务、拒绝任务、故障注入和恢复对账。每次报告绑定 DSH、模型、工具合同和任务集版本，注明实际运行范围。
- 文档证据验证通过只说明源码引用结构有效；上游测试通过、公司接口兼容、真实平台任务成功是另外三个验收阶段。

## 5. P2：工作台体验与模型运维

### 5.1 三栏界面

左栏导航，中栏文件/任务/结果/图表，右栏 DSH 对话继续沿现有产品方向。工作台可借鉴事件订阅、断线重连、去重和声明式 UI，但所有业务状态由服务端授权事件投影而来。

桌面端与网页端共用账号和后台状态，分别验收连接恢复、审批 UI 一致性、资产访问与任务事实一致性。前端订阅到某条状态不等于已获操作权限。

### 5.2 模型服务和费用

先验收公司现有 DeepSeek/本地模型：协议、tool calls、流式、取消、并发、上下文、结构化输出、拒绝与超时。Ollama/llama.cpp/vLLM 是服务方式候选，LiteLLM 是可选代理，不是必装串联链路。

模型 token 费用、QPU 使用费、HPC 节点时费用与企业配额分别对账。公司平台继续管理业务结算；网关只负责其真实覆盖的模型成本与限额。

## 6. 引入条件与退出条件

每项候选至少说明：补偿哪个缺口、是否已有公司实现、数据出网面、许可证边界、部署成本、故障影响、版本锁定及替换成本。不满足明确需求的组件暂缓引入，而不是为了覆盖调研清单而安装。

退出条件是具体且可测试的：候选无法在受管环境禁用外发、无法保持设备审批、必须引入第二 Agent 循环、不能拒绝坏信封或不能保持资源身份边界时，不用于生产路径。可以保留在隔离测试或机制参考范围。
