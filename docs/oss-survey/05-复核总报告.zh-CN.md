# 开源调研复核总报告

日期：2026-10-22。研究范围为原清单 57 个独立项目，逐项证据见 [复核索引](reviewed/README.zh-CN.md)。本报告是架构选型和源码研究结论，不是组件已部署、平台已连通或商业产品已验收的声明。

## 1. 对公司的答案

**继续采用 DSH + 公司本地模型 + 受管插件/MCP + Skills。重点补齐统一身份授权、可靠执行记录、作业对账和结果分析，而不是换 Agent 框架。**

公司已有成熟云平台、HPC 与本地模型，且代码已经有合同策略、工具注册、provider 校验、短结果和执行诊断。开源组件应帮助降低具体模块的实现成本，不替换这些业务事实源，也不把“通用能力”误等同于开放任意 shell 或安装多个 Agent runtime。

对外产品最重要的是同一用户在网页端和桌面端看到相同的服务开通、工具可用性、审批状态、任务事实和账单。仅有聊天 UI、模型回答或平台页面嵌入，不能证明这条链已完整。

## 2. 复核改变了哪些决定

### 2.1 从“按组件凑功能”转为“按缺口选组件”

旧稿给出的安装暗示过多。例如把 Ollama、llama.cpp 和 LiteLLM 串成必需链路，或默认引入图谱、向量库及完整 trace 平台。复核后的原则是保留公司当前服务；某项接口、吞吐、治理或观测确有缺口时，再做候选验证。

### 2.2 从“权限 UI”转为“服务端可验证授权”

工具过滤、只读注解、按钮开关、Skill 文本与协议认证各有作用，但都不等于某个用户被允许提交某项量子/HPC 作业。公司合同、preset、provider 和主体权限需要在真正派发前共同成立。

### 2.3 从“记忆能恢复”转为“外部副作用必须对账”

检查点保存的是框架状态，不是硬件执行事务。平台已经受理但响应丢失时，重复运行会造成重复资源占用或费用；设备必须保持零自动重试，查询事实后再处理。

### 2.4 从“有 trace”转为“明确日志、审计与账单职责”

观测平台便于调试和评估，不能自动提供合规审计、统一身份或最终结算。模型成本、HPC 节点时和 QPU 用量分别归属真实计费系统；Agent 负责关联和展示。

## 3. 建议优先复用的机制与候选

### 协议与工具工程

参考 FastMCP、MCP Python/TypeScript SDK、官方参考 servers、Inspector、GitHub MCP、Docker MCP Gateway。

- 可复用协议库和开发期检查器，避免自写 MCP 协商、传输和 schema 管道。
- 借鉴工具集收缩、清单快照、配置版本化、凭据仅在服务端注入。
- 生产候选必须经公司执行期合同验证；不把远程 catalog 自动纳入 system-trust，不因 MCP 声明只读而免除业务检查。
- GitHub/MCP 示例带来的可靠工程模式不意味着量子权限已经解决；Qiskit 两个项目只作量子作业接口参考，公司不直接执行其中科学包。

### 评估与故障注入

参考 Promptfoo、Inspect、SWE-bench、simple-evals、Vivaria，以及各产品自带测试。

- 确定性合同门禁优先于模型判分：坏信封、错误句柄、设备免审、敏感正文、未知工具必须固定失败。
- 将红队样本生成、模型评分和产品执行分开；评估器不是第二生产 runtime。
- 基准可借鉴版本绑定、环境可复现、超时清理与结果归档；公开分数不能推断公司量子任务完成率。
- 远程生成和遥测默认行为须单独审查。内网评估使用批准端点与脱敏任务集。

### 观测与跨端事件

参考 OTel 语义约定、Langfuse、Phoenix、AgentOps、CopilotKit 与 Continue/Cline 的界面桥接。

- OTel 可统一模型与工具的关联信息，业务能力/资源字段使用明确自定义命名，不劫持模型 provider 字段。
- 可靠审计记录与观测导出解耦，先保留真实执行状态再处理导出失败；不默认采集完整 prompts、工具参数或科学结果。
- 三栏 UI 可借鉴事件订阅、状态投影、断线重连和审批交互，仍由 DSH 运行对话；UI state 不是权限源。
- Langfuse/Phoenix/AgentOps 是重叠候选，不建议为“功能齐全”同时部署三套。

### Skills、资料与知识入库

参考 anthropics/skills、Superpowers、Repomix、Aider、Mem0、Graphiti、Cognee、Firecrawl 和 LLMLingua。

- 标准技能元数据、索引式装载、验证脚本和来源记录值得复用；技能文本与脚本均需准入。
- 入库先实现来源、版本、权限、有效期、撤回，再决定向量或图谱后端；自动记忆不能绕过人工审核和数据域。
- 代码打包、摘要、图谱抽取或压缩均不得提高内部资料的可见范围。
- Firecrawl/各文档技能等的许可证边界逐项审查；不把“可看源码”理解为可无条件集成，也不笼统禁止所有 AGPL 使用。

### 执行隔离

参考 E2B、microsandbox、Daytona、container-use、OpenHands、Open Interpreter、smolagents、Cloudflare Agents。

- 借鉴进程生命周期、资源限额、工作区差异、凭据注入与网络治理设计。
- Python import 限制、容器声明或云服务 API 不是强隔离证明；需要在目标 WSL2/服务器/HPC 环境验证。
- 公司现有 HPC 的受管执行能力优先复用；额外沙箱只补现有平台没有的通用代码执行需求。
- 无论隔离强度如何，设备审批和平台账号授权始终独立执行。

## 4. 只借机制、不引入生产运行时的项目

OpenCode、gptme、Goose、OpenHands、SWE-agent、mini-swe-agent、Cline、smolagents、Pydantic AI、Letta、OpenAI Agents、Google ADK、Mastra、open-swe、LangGraph、Open Interpreter 等可提供审批、状态、工具、恢复或测试样本。

其中的模型/会话/工具循环不进入公司生产链路。某个项目包含可独立使用的库、协议类型或测试模块时，可以另行评估该模块，不能因此整套接入。

“不可引入第二 runtime”与“不能研究或隔离测试别的框架”不同。本轮按各篇声明范围阅读它们，是为了理解机制、识别反例，不是给每家都找一处生产依赖。

## 5. 本地模型服务的取舍

Ollama、llama.cpp server、vLLM 和 LiteLLM 分别提供不同服务或代理能力，选择取决于公司当前部署、模型格式、硬件、并发和接口需求，而不是调研清单排序。

优先对既有端点测六件事：工具调用形状、流式事件、取消/超时、上下文边界、结构化输出、并发/限额。服务声明 supports tools 不等于某款模型在业务任务中稳定选对工具。约束解码也不等于科学指标正确或获准执行。

如果当前部署已覆盖需求，保持不变即可。S1 模型服务仍按 v0.8 定位为验收而不是公司自研网关项目。

## 6. 公司真正应拥有的部分

1. 统一账号到云/HPC 权限的映射，服务开通审批及跨端一致状态。
2. 工具/preset/provider 的合同，设备审批、严格参数与短结果约束。
3. 外部作业关联、状态对账、取消语义和结果不确定性处理。
4. 结果分析模板的输入、单位、完整性、权限及图表安全规则。
5. 内外部知识和技能的来源、范围、发布、有效期及撤回制度。
6. 固定版本的合同门禁、效果回归和真实任务验收记录。

这六项不能由任意一个 MCP gateway、观测平台或聊天 UI 自动提供。它们应直接围绕现有公司平台接口实现，而不是在 Agent 侧再造云平台/HPC。

## 7. 优先级与交付判据

**第一阶段：可信地看见和操作现有服务。** 统一身份/开通状态、会话工具可见性、执行授权、真实探测、审批关联和作业对账。

**第二阶段：可信地回收和分析结果。** 平台资产引用、完整性/单位检查、分析模板、授权图表和知识沉淀。

**第三阶段：扩展通用能力和产品体验。** 受管 Skills、文件/代码/网页工具，跨端恢复和适当观测；仍不开放绕审批的通用 shell 路径。

每阶段必须有失败反例和真实环境证据，不能仅以模型回答“已完成”、UI 显示绿色或文档已写作为验收。细化文件落点与反例见 [工程衔接建议](04-工程衔接建议.zh-CN.md)。

## 9. 商业化开发计划基线

基于本次开源源码复核、本地 DSH/合同边界和已落地的 P0/P1/P2，已形成[约 2000 人天的详细商业化开发计划](../company-agent-2000-person-days-development-plan-v1.0.zh-CN.md)，并提供[机器可读分解](../company-agent-2000-person-days-development-plan-v1.0.json)。

计划将工作拆成1740人天基线与260人天风险储备，覆盖通用Agent能力、统一账号与租户、云/HPC/量子适配、三栏Web/本地UI、结果分析、知识/Skills、运营、计费对账、安全、性能、试点和交接。公司已有DSH、本地模型、成熟云平台和HPC被作为复用前提，未重复建设基础模型、推理引擎、HPC调度器、QPU控制系统或商业账本。

建议用12–15名核心成员按14–18个月安排；核心日历仍受正式provider身份、平台接口、测试租户、审批窗口、账单映射和安全验收制约。2000人天是条件性立项基线，不是发布日期承诺。启动前10个工作日必须完成接口确认和双租户窄链验证，再决定是否释放风险储备。

## 10. 结果可信度说明

本轮针对固定源码快照的指定子系统分析实现和已有测试，许可证按各篇实际文件记录。各篇不是完整仓库逐行审计，覆盖深度不同；文档数量和证据校验通过均不能推导全框架已深读。引用与项目计数可自动验证；跨文件语义仍需人工复核。上游运行测试、公司模型压力测试、多租户攻击验证、QPU/HPC 真任务、商业许可审查没有在这轮执行。

实际证据量、校验结果与静态测试缺口见 [验证记录](06-验证记录.zh-CN.md)。本报告的“完成”仅用于源码调研范围，不用于工程上线或商业就绪声明。
