# 软件工程与前端测试工作流

## 1. 目标

让上游 Super-agent 驱动的编码 Agent 能够：

- 从规格生成可审查的实现计划
- 在隔离工单目录中修改代码
- 先写测试再实现
- 运行后端、前端、集成和端到端测试
- 完成静态安全与依赖扫描
- 生成可合并的 PR
- 在失败时给出可复现证据

执行底座是开源 Super-agent 的 Ticket 与 Executor，不是本工程自建的多会话路由器。接入假设、两套时钟和降级见 `docs/15_Super-agent接入与两套时钟.md`。上游未冻结时，一张工单对应一次 headless 会话，装配标记 `degraded`，门禁不变。

同时保证：

- Agent 不能越权
- 不能污染主分支
- 不能访问生产数据
- 不能跳过质量门禁

## 2. 需求入口

### 2.1 需求必须包含

```text
背景与问题
目标
非目标
用户与场景
验收标准（可执行）
约束（时间、兼容性、性能、安全）
依赖
风险
```

### 2.2 需求质量门

- 验收标准必须是可执行断言，不是“体验良好”。
- 必须说明失败时的行为。
- 必须说明数据迁移与回滚。
- 必须说明安全与隐私影响。

## 3. 设计与计划

### 3.1 设计输出

- 接口（请求、响应、错误码）
- 数据模型与迁移
- 状态机
- 失败模式与降级
- 观测点
- 测试策略

### 3.2 计划拆分

每个任务满足：

- 可在单个上下文完成。
- 有精确文件路径。
- 有验证命令。
- 有完成定义。
- 不依赖未完成任务。

推荐粒度：30 分钟到 2 小时。

## 4. 隔离工作区

- 每个工单一份 Git worktree 或独立克隆，由上游 Executor 持有；降级路径由本工程创建。
- 独立容器。
- 独立依赖缓存。
- 独立测试数据库。
- 独立临时目录。
- 任务结束清理。

禁止：

- 多个 Agent 共享同一工作区。
- 直接在主分支修改。
- 复用其他任务的构建缓存（除非明确安全）。

## 5. TDD 流程

```text
1. 写一个失败测试
2. 运行，确认失败原因是预期的
3. 写最小实现
4. 运行，确认通过
5. 重构
6. 运行全部相关测试
7. 提交
```

硬规则：

- 没看到失败，不算 TDD。
- 测试通过后不得无理由修改测试。
- 修复 bug 必须先有复现测试。
- 不允许用 `skip` 或 `xfail` 掩盖失败。

## 6. 测试分层

| 层 | 目的 | 工具 | 要求 |
|---|---|---|---|
| 单元 | 函数与模块行为 | pytest | 快、稳定、无外部依赖 |
| 性质 | 不变量与边界 | Hypothesis | 覆盖异常输入 |
| 集成 | 服务与依赖 | Testcontainers | 真实数据库/队列 |
| 契约 | API 兼容 | schema 测试 | 请求/响应校验 |
| E2E | 用户路径 | Playwright | 三大浏览器引擎 |
| 视觉 | UI 回归 | 截图基线 | 关键页面 |
| 性能 | 阈值 | 基准脚本 | 首屏与关键交互 |
| 安全 | 漏洞 | Semgrep/CodeQL | 高危阻断 |
| 供应链 | 依赖与镜像 | Trivy/Syft | 高危阻断 |

## 7. 前端工作流

### 7.1 本地验证

```text
启动依赖（容器）
→ 启动前端开发服务器
→ 启动后端或 mock
→ 运行组件测试
→ 运行 E2E
→ 收集 trace/截图
→ 修复
→ 重跑
```

### 7.2 Playwright 使用规范

- 使用语义定位（role、label、text），不用脆弱的 CSS 路径。
- 不使用固定 sleep，用自动等待。
- 每个测试独立浏览器上下文。
- 失败时保留 trace、截图、视频。
- 外部服务必须 mock 或使用测试环境。
- 测试数据必须可重复生成。

### 7.3 前端 Agent 的检查清单

- [ ] 页面能启动
- [ ] 关键路径可点击
- [ ] 表单校验正确
- [ ] 错误状态可见
- [ ] 加载状态可见
- [ ] 空状态可见
- [ ] 移动端布局可用
- [ ] 控制台无错误
- [ ] 网络请求无 4xx/5xx 意外
- [ ] 截图与基线对比通过

## 8. 代码审查

### 8.1 审查维度

| 维度 | 检查 |
|---|---|
| 正确性 | 是否满足需求与验收标准 |
| 边界 | 空值、超时、重试、并发 |
| 安全 | 注入、越权、密钥、日志泄漏 |
| 性能 | N+1、无界内存、阻塞 |
| 可维护 | 命名、分层、重复 |
| 测试 | 覆盖关键路径与失败路径 |
| 兼容 | API、数据、配置 |
| 可观测 | 日志、指标、trace |

### 8.2 分级

- **阻断**：正确性、安全、数据丢失、越权。
- **重要**：性能、可维护、测试缺失。
- **建议**：风格、命名、注释。

阻断项未解决不得合并。

## 9. 合并门禁

```text
[ ] 单元测试通过
[ ] 性质测试通过
[ ] 集成测试通过
[ ] 契约测试通过
[ ] E2E 通过
[ ] 视觉回归通过（如适用）
[ ] 静态安全无高危
[ ] 依赖扫描无高危
[ ] SBOM 已生成
[ ] 覆盖率不低于阈值
[ ] 审查阻断项已解决
[ ] 人工审批通过（按风险）
[ ] 回滚方案已记录
[ ] 变更日志已更新
```

## 10. 发布

### 10.1 发布前

- 版本号与变更日志。
- 数据库迁移演练。
- 回滚演练。
- 灰度计划。
- 监控与告警。
- 值班安排。

### 10.2 发布中

- 灰度比例。
- 关键指标观察。
- 自动回滚阈值。
- 人工确认点。

### 10.3 发布后

- 错误率、延迟、资源。
- 用户反馈。
- 自动创建后续 Issue。

## 11. DSH 插件落法

| 能力 | 插件/服务 | 说明 |
|---|---|---|
| 需求结构化 | `ctx.goal` | 生成任务草案，并形成规格 |
| 授权范围 | 上游 Mandate | 规格是范围；本工程不保存第二套工单状态机 |
| 计划 | Superpowers 技能 | 计划文件落对象存储 |
| 工作区 | 上游 Executor | 一工单一目录；降级时用 `ctx.software` 的 worktree |
| 测试 | 门禁命令 | pytest / Playwright，结果写入证据 |
| 审查 | 独立评审工单或 pr-agent | 作者 Agent 不审自己的 PR |
| 门禁 | 平台策略 | 服务端强制；Watchdog 与投机执行不能跳过 |
| 发布 | 平台 | 人工审批 |

## 12. 反模式

1. 让 Agent 直接推主分支。
2. 只跑单测就合并。
3. 用 mock 覆盖所有集成风险。
4. 失败测试被跳过。
5. 用固定 sleep 等待页面。
6. 用 CSS 选择器定位易变元素。
7. 在生产数据上跑 E2E。
8. 安全扫描只在发布前跑一次。
9. 没有回滚方案。
10. 审查只看风格不看边界。
11. 在本工程重写一套 Router / Worker 来代替上游 Super-agent。
12. 让作者工单审查并合并自己打开的 PR。
